                      COC-SONARLINT REFERENCE MANUAL


SonarLint extension for coc.nvim         *coc-sonarlint* *coc-sonarlint-intro*

coc-sonarlint runs the SonarLint language server of Sonar (here "the server")
in coc.nvim. It analyzes the files you edit and reports quality and security
issues as diagnostics, offers quick fixes as code actions, shows rule
descriptions, and lists findings, rules and security hotspots in tree views.

This page describes how to use the extension. Requirements, installation,
setup and settings are in the README of the extension. The extension adds
this page to 'runtimepath' when it is activated, no |:helptags| is needed.

                                      Type |gO| to see the table of contents.

==============================================================================
GETTING STARTED                                          *coc-sonarlint-start*

Open a file of a supported language. The extension starts on C, C++, CUDA,
Objective-C, OpenCL, Java, C#, VB, PHP, Go, Python, Jupyter, JavaScript,
TypeScript and their React variants, CSS, Less, SCSS, YAML and JSON files,
or when the workspace contains a `.sonar.properties` file. It starts the
server for you; the first analysis runs when the server is ready.

If nothing is reported, open the log with
|coc-sonarlint-SonarLint.ShowSonarLintOutput| and see Troubleshooting in the
README, which also lists the warnings you can get.

==============================================================================
DIAGNOSTICS                                        *coc-sonarlint-diagnostics*

Issues show up like those of any other language server: signs, virtual
text, |:CocDiagnostics| and the diagnostic list. With
`sonarlint.automaticAnalysis` enabled (the default), open files are analyzed
as you type. Files changed on disk outside the editor are analyzed
`sonarlint.changedFilesAnalysisDebounceMs` (1000 ms) after the last change.

To analyze on demand use |coc-sonarlint-SonarLint.AnalyseOpenFile|,
|coc-sonarlint-SonarLint.AnalyzeVCSChangedFiles| or
|coc-sonarlint-SonarLint.AnalyzeWorkspace|. The last two open the findings
tree when they finish.

==============================================================================
CODE ACTIONS                                      *coc-sonarlint-code-actions*

On a line with an issue, |<Plug>(coc-codeaction-cursor)| (or your code
action mapping) lists what the server offers for it: quick fixes that edit the
code, opening the description of the rule, and deactivating the rule.
Deactivating writes the rule to `sonarlint.rules` in your settings.

==============================================================================
RULE DESCRIPTIONS                                        *coc-sonarlint-rules*

Rule descriptions open in the rule view, see |coc-sonarlint-views|. Open one
from a code action, from the rules tree, or by key with
|coc-sonarlint-SonarLint.OpenRuleByKey|, which accepts a rule key such as
`java:S1234` or a language.

|coc-sonarlint-SonarLint.ShowAllRules| opens the rules tree, and
|coc-sonarlint-SonarLint.ShowActiveRules| and
|coc-sonarlint-SonarLint.ShowInactiveRules| filter it. Rules can be
activated and deactivated from the tree. A workspace rules file is created
with |coc-sonarlint-SonarLint.IntroduceSonarQubeRulesFile| and opened with
|coc-sonarlint-SonarLint.OpenSonarQubeRulesFile|.

==============================================================================
FINDINGS                                              *coc-sonarlint-findings*

|coc-sonarlint-SonarQube.ShowAllFindings| opens the findings tree with every
issue and hotspot known for the workspace. These commands filter it:
|coc-sonarlint-SonarQube.ShowOpenFilesOnly|,
|coc-sonarlint-SonarQube.ShowCurrentFileOnly|,
|coc-sonarlint-SonarQube.ShowHighSeverityOnly| and
|coc-sonarlint-SonarQube.ShowFixableIssuesOnly|. Selecting a finding jumps to
its location; issues with secondary locations show them in the locations
tree.

==============================================================================
SECURITY HOTSPOTS                                     *coc-sonarlint-hotspots*

Security hotspots need Connected Mode. Hotspots of open files are reported
with the issues; |coc-sonarlint-SonarLint.ScanForHotspotsInFolder| scans a
whole folder. Hotspot details open in the hotspot view, see
|coc-sonarlint-views|, and the status of a hotspot can be changed when the
server allows it.

==============================================================================
CONNECTED MODE                                  *coc-sonarlint-connected-mode*

Connections and bindings are set up in the settings, see the README.
|coc-sonarlint-SonarQube.ShowConnectionView| opens the connections tree,
|coc-sonarlint-SonarLint.AutoBindWorkspaceFolders| binds the workspace
folders to matching remote projects, and
|coc-sonarlint-SonarLint.ShareConnectedModeConfiguration| writes the binding
to a file that can be committed for the team. The details of a connection
in the tree open in the connection view, see |coc-sonarlint-views|.

==============================================================================
DESCRIPTION VIEWS                                        *coc-sonarlint-views*

Rule descriptions, hotspot details and connection details are shown as
styled text in a scratch buffer, one per kind: `sonarlint://rule`,
`sonarlint://hotspot` and `sonarlint://connection`. The Connect commands
show a read-only preview of their form in `sonarlint://connection-setup`.
Opening another rule replaces the content of the rule buffer, reuses its
window when it is visible and moves the focus into it. The buffer is
read-only and not listed, and its 'filetype' is `htmlview`.

The statusline (or the float title) names the rule key and the rule name
for a rule, the rule key and the message for a hotspot, and "Connection"
plus the connection id (or the server product name in the form preview)
for the connection views.

The views render the description the way a browser would: HTML and CSS
decide how it looks. Headings, emphasis, inline code, code blocks, lists,
block quotes, rules, tables with borders, definition lists, banners and the
colored capsules of a rule all keep their shape, and boxes are drawn with
border characters. The text is laid out for the width of the window and
laid out again when the window is resized. Code blocks keep their lines and
are never wrapped.

Description tabs work like tabs in a browser: only the selected tab is
shown. Where a rule explains the fix for several frameworks, a bar of their
names sits above the fix and only the selected one is shown, highlighted in
the bar: >
    Servlet  JSP  Spring
<
Select a tab or a framework with <CR>, see |coc-sonarlint-view-keys|.

The address of a link is shown after its text, as ` 🔗 url`. In Neovim it is
virtual text: it is not part of the buffer, so it is not yanked or searched.
In Vim it is ordinary buffer text.

Settings ~
The window of the view (split or float, the split command) is set with the
`htmlview.view.mode` and `htmlview.view.splitCommand` settings of the optional
coc-htmlview extension. Without it descriptions open in a simple floating
window.

                                           *coc-sonarlint-view-stylesheets*
sonarlint.view.stylesheets    Default `[]`.
    A list of CSS files passed to coc-htmlview after the bundled stylesheets
    of every view, so their rules win. Only `style` attributes in the HTML come later.
    `~` and environment variables are expanded, and a relative path is
    taken from the workspace root. A file that cannot be read is skipped
    and named in the SonarLint output. See |coc-sonarlint-view-styles|.

Keys ~
                                                  *coc-sonarlint-view-keys*
These keys are mapped in the view buffer (Normal mode):

    q           Close the view.
    <CR>        Follow the link under the cursor: open a URL, jump to a
                section, or select the tab or framework under the cursor.
    gx          Open the URL under the cursor in the browser.
    <Tab>       Move to the next link.
    <S-Tab>     Move to the previous link.
    ]]          Jump to the next heading.
    [[          Jump to the previous heading.
    ]c          Select the next framework of the fix under (or above) the
                cursor.
    [c          Select the previous framework.

Styles and highlight groups ~
                                                *coc-sonarlint-view-styles*
The cascade is the one of a browser. Rules come from, in order: a built-in
default stylesheet (what a browser does for headings, lists, tables and so
on, adapted to the terminal), the stylesheets SonarLint uses in VS Code,
bundled with the extension, a small sheet of ours that draws their tabs as
a tab bar instead of boxes, drops padding that would become blank lines and
draws the boxes in the tabs and the capsules with a faint line, your own
list, see |coc-sonarlint-view-stylesheets|, and finally `style` attributes
in the HTML. Later sources win, `!important` and the specificity of selectors
count as usual, and properties are inherited.

Their theme follows 'background' (light or dark). It is updated when the
|ColorScheme| event fires and when 'background' is set.

Every style becomes a highlight group named `HtmlView` plus the words of
its CSS class or selector, for example `HtmlViewH1`,
`HtmlViewImpactHigh`, `HtmlViewCodeAdded` or `HtmlViewHljsKeyword`.
The colors of the stylesheets come from groups named after VS Code's theme
colors, for example `HtmlViewVscodeTextLinkForeground`. Each of them is
linked to a role group, `HtmlViewHost` plus the role, which in turn is
linked to a standard group of your colorscheme, so the views follow it:

    Borders, rules, boxes   |hl-FloatBorder|
    Headings                `@markup.heading.1` to `.6`, else `Title`
    Links                   `@markup.link` (else `Underlined`); the
                            ` 🔗 url` text uses `@markup.link.url`
    Inline code, `kbd`      `@markup.raw`
    Bold, italic            `@markup.strong`, `@markup.italic`
    Block quotes, muted     `@markup.quote`, |hl-Comment|
    List markers            `@markup.list`
    Added, removed code     |hl-DiffAdd|, |hl-DiffDelete|
    Passed, failed, warn    `DiagnosticOk`, `DiagnosticError`,
                            `DiagnosticWarn`, `DiagnosticInfo`

Roles whose first group is not defined by your colorscheme fall back to the
next one, for example `@markup.heading` and then `Title`.

All of them are defined as defaults: a group you define yourself wins. Since
|:colorscheme| clears highlights, define overrides in a |ColorScheme|
autocommand: >
    autocmd ColorScheme * hi HtmlViewH1 gui=bold guifg=#e0af68
          \ | hi link HtmlViewHostLink Function
<
Use :filter /HtmlView/ highlight to list the groups. For larger changes,
add your own CSS with |coc-sonarlint-view-stylesheets|: it can use the class
names of the bundled stylesheets and the `--vscode-*` variables.

Code highlighting ~
                                             *coc-sonarlint-view-code*
Code blocks are highlighted with the language of the rule. In Neovim each
block uses its treesitter parser when one is installed for the language,
with your colorscheme's treesitter colors. Blocks without a parser, and
every block in Vim, are highlighted with the bundled highlight.js grammars
instead, through the `HtmlViewHljs*` groups. In compliant and noncompliant
examples the changed lines are marked with a |hl-DiffAdd| or |hl-DiffDelete|
background under the syntax colors.

In Vim the views show the same text and colors with simpler highlighting.

==============================================================================
LOGS                                                      *coc-sonarlint-logs*

The extension logs to the coc output channel `Sonarlint`.
|coc-sonarlint-SonarLint.ShowSonarLintOutput| opens it,
|coc-sonarlint-SonarLint.EnableVerboseLogs| turns on verbose logs, and
|coc-sonarlint-SonarLint.EnableLogsAndShowOutput| does both.

==============================================================================
COMMANDS                                              *coc-sonarlint-commands*

Run the commands with |:CocCommand| or from |coc-list-commands|.

:CocCommand SonarLint.OpenSample          *coc-sonarlint-SonarLint.OpenSample*
    Open Sample Project. Open sample to explore SonarLint features.

:CocCommand SonarLint.ShowAllRules      *coc-sonarlint-SonarLint.ShowAllRules*
    Show All Rules. Open rules view for SonarLint rules.

:CocCommand SonarLint.OpenRuleByKey    *coc-sonarlint-SonarLint.OpenRuleByKey*
    Open Rule by Key…. Show details for a rule (e.g., java:S1234).

                                     *coc-sonarlint-SonarLint.ShowActiveRules*
:CocCommand SonarLint.ShowActiveRules
    Show Active Rules. Display the rules that are currently active.

                                     *coc-sonarlint-SonarLint.AnalyseOpenFile*
:CocCommand SonarLint.AnalyseOpenFile
    Analyze Active File. Run analysis on the currently active file,
    and warn when no file is open.

                              *coc-sonarlint-SonarLint.AnalyzeVCSChangedFiles*
:CocCommand SonarLint.AnalyzeVCSChangedFiles
    Analyze VCS Changed Files. Analyze the files git reports as changed:
    uncommitted changes and commits not yet pushed to the reference branch.

                                     *coc-sonarlint-SonarQube.ShowAllFindings*
:CocCommand SonarQube.ShowAllFindings
    Show All Findings. List all issues found in the workspace.

                                     *coc-sonarlint-SonarLint.HelpAndFeedback*
:CocCommand SonarLint.HelpAndFeedback
    Help & Feedback. Open SonarLint documentation and community links.

                                   *coc-sonarlint-SonarLint.ShowInactiveRules*
:CocCommand SonarLint.ShowInactiveRules
    Show Inactive Rules. Display rules not currently active.

                                   *coc-sonarlint-SonarLint.EnableVerboseLogs*
:CocCommand SonarLint.EnableVerboseLogs
    Enable Verbose Logs. Increase logging detail to verbose.

                                   *coc-sonarlint-SonarLint.InstallManagedJre*
:CocCommand SonarLint.InstallManagedJre
    Install Managed JRE. Download and configure a managed JRE.

                                   *coc-sonarlint-SonarQube.ShowOpenFilesOnly*
:CocCommand SonarQube.ShowOpenFilesOnly
    Show Findings for Open Files. Filter findings on currently opened files.

                                  *coc-sonarlint-SonarQube.ShowConnectionView*
:CocCommand SonarQube.ShowConnectionView
    Show Connections. Open the Connections view.

                                 *coc-sonarlint-SonarQube.ShowCurrentFileOnly*
:CocCommand SonarQube.ShowCurrentFileOnly
    Show Findings for Current File. Filter the findings for active file only.

                                 *coc-sonarlint-SonarLint.ShowSonarLintOutput*
:CocCommand SonarLint.ShowSonarLintOutput
    Show SonarLint Output. Open the SonarLint output.

                                *coc-sonarlint-SonarQube.ShowHighSeverityOnly*
:CocCommand SonarQube.ShowHighSeverityOnly
    Show High Severity Only. Filter findings to high-severity issues.

                               *coc-sonarlint-SonarLint.ShowMCPConfigurations*
:CocCommand SonarLint.ShowMCPConfigurations
    Show MCP Configurations. Show MCP configuration settings.

                               *coc-sonarlint-SonarQube.ShowFixableIssuesOnly*
:CocCommand SonarQube.ShowFixableIssuesOnly
    Show Fixable Issues Only. Filter findings that have available quick fixes.

                              *coc-sonarlint-SonarLint.OpenSonarQubeRulesFile*
:CocCommand SonarLint.OpenSonarQubeRulesFile
    Open SonarQube Rules File. Open rules configuration file, if present.

                             *coc-sonarlint-SonarLint.EnableLogsAndShowOutput*
:CocCommand SonarLint.EnableLogsAndShowOutput
    Enable Logs and Show Output. Enable verbose logs and open the SonarLint
    output.

                             *coc-sonarlint-SonarLint.ScanForHotspotsInFolder*
:CocCommand SonarLint.ScanForHotspotsInFolder
    Scan Folder for Security Hotspots. Run a hotspot scan in a chosen folder.

                                    *coc-sonarlint-SonarLint.AnalyzeWorkspace*
:CocCommand SonarLint.AnalyzeWorkspace
    Analyze Workspace. Analyze every supported file in the workspace, whether
    open or not (works in standalone mode, unlike hotspot scanning).

                            *coc-sonarlint-SonarLint.AutoBindWorkspaceFolders*
:CocCommand SonarLint.AutoBindWorkspaceFolders
    Auto-Bind Workspace Folders. Bind the workspace folders to matching
    projects of your connections.

                          *coc-sonarlint-SonarLint.OpenMCPServerConfiguration*

    Open MCP Server Configuration. Open configuration for MCP servers.

                         *coc-sonarlint-SonarLint.IntroduceSonarQubeRulesFile*

    Create SonarQube Rules File. Add a rules file to the workspace.

                        *coc-sonarlint-SonarLint.ConfigureCompilationDatabase*

                     *coc-sonarlint-SonarLint.ShareConnectedModeConfiguration*
:CocCommand SonarLint.ShareConnectedModeConfiguration

                                  *coc-sonarlint-SonarLint.ConnectToSonarQube*
:CocCommand SonarLint.ConnectToSonarQube
    Connect to SonarQube. Open the form for a new SonarQube connection.

                                 *coc-sonarlint-SonarLint.ConnectToSonarCloud*
:CocCommand SonarLint.ConnectToSonarCloud
    Connect to SonarCloud. Open the form for a new SonarCloud connection.

                                   *coc-sonarlint-SonarLint.ReopenLocalIssues*
:CocCommand SonarLint.ReopenLocalIssues

:CocCommand SonarLint.ClearLocations

    Do Not Focus on New Code. Turn off the sonarlint.focusOnNewCode setting.

:CocCommand SonarLint.AutomaticAnalysis.Enable
    Enable Automatic Analysis. Turn on the sonarlint.automaticAnalysis
    setting.

                           *coc-sonarlint-SonarLint.AutomaticAnalysis.Disable*
:CocCommand SonarLint.AutomaticAnalysis.Disable
    Disable Automatic Analysis. Turn off the sonarlint.automaticAnalysis
    setting.
